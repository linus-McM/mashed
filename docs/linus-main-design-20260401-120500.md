## Problem Statement

Solo AI-heavy developers running multiple Claude Code sessions across repos lose track of what's happening where. Agents finish, fail, or need a response in terminals the developer forgot about. By the time they notice, they've lost context. There is no tool that unifies multi-repo agent monitoring, notification-driven workflow, scoped code review, and worktree lifecycle management into a single development environment.

## What Makes This Cool

Reductor isn't a dashboard. It's an **attention management system for multi-agent development**. The core insight: the bottleneck in multi-agent dev isn't agent coordination (CrewAI, LangGraph solve that). It's human attention across agents. Conductor tells you what needs YOUR attention right now and scopes your entire view to only what's relevant.

Four features that nothing on the market does together:
1. **Notification-driven workflow** — agents bubble up events (finished/failed/needs-response), you click and land in the right terminal
2. **Scoped code views with diff** — drill into an agent and see only the files it touched, not the whole codebase
3. **Worktree lifecycle** — see worktrees, review diffs, prompted to merge back into the original repo
4. **Multi-repo context isolation** — when you're in a repo, only that repo's files and agents are visible

The 10x vision (post-V1): agent memory + learning, visual drag-and-drop workflow composer, autonomous fleet management.

## Constraints

- Must be a graphical IDE application (not a pure TUI), with rich UI chrome wrapping embedded terminal panes
- Go backend for process scanning, JSONL parsing, tmux control, file watching
- Web frontend via Wails for DAG visualization, diff views, notifications, drag-and-drop (future)
- Single binary distribution (Wails embeds web assets into the Go binary)
- Claude Code-specific first (JSONL parsing, session detection, agent tree are all Claude-specific)
- Must run on macOS, Linux; Windows is nice-to-have
- Must work with tmux (agents typically run inside tmux)
- Terminal embedding via xterm.js + WebSocket bridge (see Terminal Bridge section below)

## Platform Decision: Wails

**Architecture:** Go backend + HTML/CSS/JS frontend rendered in native OS webview (not Electron, no bundled Chromium).

**Why Wails over alternatives:**
- **vs Fyne:** Wails gives unlimited visual flexibility for DAG bezier curves, syntax-highlighted diffs, drag-and-drop composer. Fyne's Material Design aesthetic is too constraining for an IDE.
- **vs Gio:** Wails has a much larger ecosystem and lower barrier. Gio would require building every UI primitive from scratch.
- **vs Electron/Tauri:** Wails is Go-native. Backend is pure Go, frontend communicates via Go bindings. Single binary.

**Key Wails components:**
- Go backend: exposes functions to frontend via `wails.Bind()`
- Frontend: Svelte with xterm.js for terminal panes
- WebSocket server: Go serves terminal I/O to xterm.js instances
- Native events: Wails runtime provides system notifications, menu, window management

## Security Model

This is a **single-user desktop application**. The WebSocket terminal server binds to `localhost` only (127.0.0.1) and is not exposed on any network interface. No authentication layer is needed for V1 because the only user is the local machine owner. If SSH/remote access is added in future phases, authentication (SSH keys or token-based) must be added before that feature ships.

## Terminal Bridge: xterm.js ↔ tmux

The Go backend runs a WebSocket server on localhost. For each agent with a tmux pane:

1. **Attach:** `tmux attach-session -t {target}` via `os/exec` with a pty (using `creack/pty`)
2. **Read:** goroutine reads pty stdout → writes to WebSocket
3. **Write:** goroutine reads WebSocket (user keystrokes) → writes to pty stdin
4. **Latency:** local pty I/O is sub-millisecond; WebSocket on localhost adds <1ms. Total perceived latency is under 5ms, well within interactive threshold.

xterm.js renders in the Wails webview. **Webview compatibility note:** Wails uses WKWebView on macOS and WebKit2GTK on Linux. xterm.js v5+ supports both via its canvas renderer (default) and DOM renderer (fallback). The WebGL addon should NOT be used as it requires Chromium. Test during Phase 4 scaffolding.

**Linux WebSocket risk mitigation:** WebKit2GTK has known issues with WebSocket connections in some versions (silent drops, `wss://` failures). Mitigation: (1) Use `ws://localhost` (not `wss://`) since traffic never leaves the machine. (2) If WebSocket fails on Linux, fall back to HTTP long-polling with 100ms interval for terminal I/O (higher latency but functional). (3) Document minimum WebKit2GTK version in build requirements.

**Build note:** xterm.js and its addons (`@xterm/xterm`, `@xterm/addon-fit`, `@xterm/addon-canvas`) are npm dependencies resolved during the frontend build step (`npm install` / `pnpm install`). `wails build` then embeds the built frontend assets into the Go binary. The npm step must complete before `wails build`.

- Effort: M (CC: ~2-3 hours)
- Risk: Low-Med
- Pros: Core insight is the foundation, scoped code views land early

### Notification Event Schema

```go
type NotificationEvent struct {
    ID        string        // unique event ID (uuid)
    AgentID   string        // "pid-{pid}" or "{parentID}-sub-{name}"
    AgentName string        // model name or sub-agent description
    RepoName  string        // repository name
    RepoBranch string       // current branch
    EventType EventType     // NeedsResponse | Error | Completed | Running | Started
    Summary   string        // human-readable event summary (max 120 chars)
    Timestamp time.Time     // when the event occurred
    Read      bool          // has the user seen this event
    Priority  int           // computed: 0=needs-response, 1=error, 2=completed, 3=running
    TokensUsed int64        // current token count at time of event
    TmuxTarget string       // tmux pane target for drill-down (empty if no pane)
}

type EventType string
const (
    EventNeedsResponse EventType = "needs_response" // AskUserQuestion, permission prompt
    EventError         EventType = "error"           // tool error, test failure
    EventCompleted     EventType = "completed"       // session ended cleanly
    EventRunning       EventType = "running"         // actively producing output
    EventStarted       EventType = "started"         // new agent detected
)
```

### Data Flow

```
Go Backend (goroutines):
  Process Scanner (5s tick) → discovers agents, maps to repos
  JSONL Watcher (fsnotify)  → parses new lines, extracts events
  Notification Engine       → classifies events, sorts by priority
  WebSocket Server          → bridges tmux panes to xterm.js

  All → Wails Events → Frontend

Frontend:
  NotificationFeed ← subscribes to prioritized event stream
  AgentDetail      ← requests scoped diff, terminal WebSocket on drill-down
  Terminal         ← xterm.js connects to Go WebSocket for live tmux I/O
```

## Error Handling & Resilience

| Failure Mode | Behavior | Recovery |
|---|---|---|
| Agent JSONL file malformed | Skip malformed line, log warning, continue parsing | Auto-heals on next valid line |
| tmux pane disappears mid-session | Mark agent as "pane lost", show last known log lines | Re-scan on next 5s tick, reconnect if pane returns |
| WebSocket connection drops | xterm.js shows "Reconnecting..." overlay | Auto-reconnect with exponential backoff (1s, 2s, 4s, max 30s) |
| Agent process dies unexpectedly | Notification engine emits EventError | Process scanner detects on next tick, updates status |
| fsnotify watcher fails | Fall back to polling (1s interval) | Log warning, attempt to re-establish watcher |
| Git commands fail (repo corrupted) | Show repo as "unavailable" in notification feed | Skip repo, do not crash |

| Short-lived agent (< 5s) | May miss process scan | Detected via fsnotify on new JSONL session files (see below) |

Principle: **Conductor never crashes because an agent crashes.** Each module degrades independently.

**Short-lived agent detection:** The 5s process scan interval may miss agents that start and exit quickly. Supplement with fsnotify watching `~/.claude/projects/` for new `.jsonl` files. A new file appearing triggers immediate session parsing regardless of the process scan timer. This gives near-instant detection of all agent starts.

## JSONL File Format Reference

Session files live at `~/.claude/projects/{repo-key}/{session-id}.jsonl` where `repo-key` is the repo's absolute path with `/` replaced by `-` (e.g., `/Users/linus/Development/mashed` → `-Users-linus-Development-mashed`).

Each line is a JSON object with a `"type"` field:
- `"assistant"` — contains `message.usage` (token counts: `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`) and `message.content` (array of `tool_use` and `text` blocks)
- `"user"` — contains `message.content` (array of `tool_result` blocks)

**Event detection logic for each EventType:**

| EventType | Detection Signal |
|---|---|
| `EventNeedsResponse` | `tool_use` block with `name: "AskUserQuestion"` and no subsequent `tool_result` with matching `tool_use_id` |
| `EventError` | `tool_result` where content contains error keywords ("Error:", "failed", "FAIL", exit code != 0); or `tool_use` with `name: "Bash"` followed by `tool_result` containing stderr |
| `EventCompleted` | Agent process no longer in `ps` output AND last JSONL line has no pending `tool_use` without a matching `tool_result` |
| `EventRunning` | New JSONL lines written within the last 10 seconds (via fsnotify timestamp) |
| `EventStarted` | New session file appears in `~/.claude/projects/{repo-key}/` (via fsnotify on directory) OR new PID detected by process scanner |

**Sub-agent identification from JSONL:**
When a `tool_use` block has `name: "Agent"`, the `input` object contains `name` (sub-agent name) and `description` (task description). The `tool_use.id` (e.g., `"toolu_01..."`) becomes the key for this sub-agent. When a `tool_result` arrives with a matching `tool_use_id`, the sub-agent is marked as completed. The parent agent is the session that produced the `tool_use` block. Sub-agent ID format: `"{parentAgentID}-sub-{input.name}"`.

Full parsing spec: `SPECIFICATION.md` sections 3-6 in the project root.

## Reviewer Concerns

After 3 rounds of adversarial review, these implementation-level details remain for the engineer to resolve during build:

1. **Sub-agent ID collision:** If two sub-agents share the same `name` under the same parent, IDs collide. Fix during implementation: append `tool_use.id` to the sub-agent ID format.
2. **JSONL repo-key leading slash:** The repo-key derivation should explicitly state the leading `/` is included (producing `-Users-linus-...` not `Users-linus-...`).
3. **WebSocket concurrency model:** With 5-10 simultaneous terminal connections, document: one goroutine pair per connection (read + write), pty cleanup on WebSocket close, bounded write buffer (64KB ring buffer) for slow consumers.
4. **Linux long-polling fallback:** HTTP long-polling at 100ms is degraded-mode only. For smooth terminal interaction, either lower to 16ms (higher CPU) or accept degraded UX and state this explicitly. Prefer fixing WebSocket on Linux over falling back.
5. **SPECIFICATION.md section references:** If the spec is reorganized, section number references break. During implementation, cross-reference by section title, not number.
